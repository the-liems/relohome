# SPEC-015: Maps and location experience

Status: Draft. Owner: unassigned. Reviewers: map/location, housing, moving, AI system, frontend. Updated: 2026-10-05. This specification defines required customer-facing behavior for review; acceptance and implementation status are separate.

Related: [product brief](../product.md), [SPEC-008: Domain MCP tool catalogue](SPEC-008-service-tools.md), [Housing work #6](https://github.com/AI20K-Build-Phase-Cohort-4/P-044/issues/6).

Implementation parent: [Map work #7](https://github.com/AI20K-Build-Phase-Cohort-4/P-044/issues/7). Application integration: [#21](https://github.com/AI20K-Build-Phase-Cohort-4/P-044/issues/21). Requirements review: [#30](https://github.com/AI20K-Build-Phase-Cohort-4/P-044/issues/30).

Shared interaction and prompt-placement review: [#28](https://github.com/AI20K-Build-Phase-Cohort-4/P-044/issues/28). Its three interaction prototypes and cross-service accessibility review are separate deliverables; this specification supplies the location requirements they must satisfy.

## Problem and scope

Customers comparing homes and planning a move need to find the intended place, explore its surroundings, and understand distance or travel implications. Ambiguous names, approximate coordinates, and incomplete datasets must not become unsupported claims about a home's suitability or a moving provider's service.

This specification governs how the relocation application presents and uses Location evidence across housing, recommendation, and moving. [SPEC-007: Location Platform](SPEC-007-location-platform.md) and its linked service specifications own Location service behavior. SPEC-015 adds application requirements for clarification, evidence presentation, context changes, and selection; it does not replace their schemas or acceptance criteria.

## Required capabilities

| Feature | Expected behavior |
|---|---|
| Resolve places and addresses | Resolve supported named places and administrative areas into candidates; ask the user to choose when ambiguous. For an unresolved street address, request clarification or a user-confirmed pin. Do not promise arbitrary address geocoding. |
| Explore an area | Show places and homes in the area the user is exploring, with accessible details and source/coverage information. |
| Find nearby amenities | Find relevant facilities around a home, such as groceries or transit, without treating missing data as proof that none exist. |
| Compare routes | Show route distance and estimated duration for supported travel modes, with origin, destination, assumptions, and unavailable cases. |
| Evaluate geographic requirements | Supply evidence for requirements such as proximity or commute time; distinguish straight-line distance from a route calculation. |
| Refine through text and controls | Let users specify or correct an area, address, destination, or travel mode without losing the active task. |

## User flow

1. Capture the user's area, destination, and geographic requirements from text or controls while preserving the active housing or moving task.
2. Resolve supported names into candidates. Clarify ambiguity, missing route mode, and uncertain endpoints before using them for the affected decision.
3. Retrieve places, nearby evidence, or routes using confirmed context and supported inputs. Show pending work with the destination and mode it uses.
4. Present sourced results, units, assumptions, accuracy, and unavailable cases in both map and text/list views. Let the user refine requirements or choose a location.
5. Apply the choice to application state and recompute affected evidence. Housing selection and each consequential vendor action retain their own decision and approval steps.

## Coverage, modes, and amenities

Product scope is independent of the city selected for a demonstration. The inspected Location branch accepts routing areas `hcm`, `hanoi`, and `danang` (Ho Chi Minh City, Hanoi, and Da Nang). These are configured routing bounds, not a promise of complete city-wide address, POI, housing, or provider coverage. Both route endpoints must be inside the selected routing area. Outside that area, explain the limitation and retain the user's requirement rather than substitute a different destination.

The supported route profiles are `driving`, `motorcycle`, and `walking`. Show the chosen profile and pass it explicitly in every routing path, including `search_housing.commute.profile`. Pass the validated city explicitly as `search_housing.commute.city` as well; do not let the service infer a different city from each listing. The service's motorcycle default must not silently decide a user's commute mode. If the user has not specified a mode, ask before sending a commute filter or assessing a commute requirement. Retain the requested city, profile, direction, and destination with the result because the housing response's bare `commute` route does not echo them. Public transport, cycling, intercity routing, live traffic, and departure-time predictions are deferred. A nearby bus stop or station is a place result, not evidence of a supported transit route.

Use these existing category slugs for common relocation requirements. These mappings select relevant categories without assuming every customer needs each one or that a dataset contains complete coverage. Ask for the intended subtype when a broad request would otherwise change its meaning.

| Customer requirement | Existing categories | Interpretation |
|---|---|---|
| Groceries | `supermarket`, `convenience_store`, `marketplace` | Offer these as distinct choices; a convenience store is not automatically a supermarket. |
| Healthcare | `pharmacy`, `clinic`, `hospital` | Preserve the requested facility type; nearby does not establish services or opening hours. |
| Education | `school`, `kindergarten`, `college`, `university` | Proximity does not establish admission, catchment, or suitability. |
| Transit access | `bus_stop`, `bus_station`, `rail_station` | Evaluate access to the place only; no timetable or passenger journey guarantee. |

Other supported categories remain available through place search. An unmapped requirement stays unresolved; do not silently map it to `other`. These slugs come from the existing category migrations linked below, not a new taxonomy.

## Location and evidence rules

1. **Ambiguity:** use city/area context when searching. Resolve an explicitly named administrative area with `search_areas`; use `resolve_location` for named places or unclear entity types. `resolve_location.ambiguous` requires clarification when true. `search_areas` has no such flag: compare its candidates with the user's supplied city, parent area, and level. If multiple candidates remain plausible, or even the sole returned candidate conflicts with those details, show labels, parent areas, and sources and ask for clarification. No results means unresolved. Neither absence of a flag, a limited result page, nor first position establishes a unique match. Treat match scores as retrieval signals, not accuracy probabilities.
2. **Precision:** preserve source coordinates and `location_accuracy` (`rooftop`, `approximate`, or `unknown`) where available. Missing accuracy remains unknown. Extra decimal places and a successful route do not establish an exact entrance. For a selected place or housing ID, prefer `calculate_route_between_entities` to retrieve endpoint metadata and warnings; a coordinate-only route does not supply these. Area centers are search context, not building entrances. Unknown accuracy does not block exploratory routes: label their evidence provisional. Before a moving handoff, obtain explicit confirmation of the address/entrance or displayed pin if accuracy remains uncertain. Reuse that confirmation for the same unchanged endpoint instead of asking after every route call; changing its ID or coordinates invalidates confirmation. Store confirmation separately from source accuracy. It does not upgrade the source label or prove provider serviceability.
3. **Distance:** `find_nearby_places` and `search_housing.nearby` both use straight-line distance. The former returns only the nearest matching place per category; the latter filters homes by that distance and can exclude them before route assessment. Neither establishes walking distance or travel time. Do not translate a walking requirement directly into a hard `nearby.max_distance_m` housing filter. Retrieve housing candidates with the other supported filters, then evaluate the walking requirement using the candidate procedure below. An explicitly requested straight-line condition may use `nearby`, with its meaning labeled. Preserve metres/seconds in service data and label displayed units and measurement type.
4. **Route assumptions:** show origin, destination, profile, distance, estimated duration, and endpoint warnings. The current request has no departure-time or live-traffic input. Label durations as route estimates, without traffic guarantees. Road snapping can move an endpoint; retain returned snap distances and warnings, and do not describe the snapped road point as a verified building entrance.
5. **Coverage and failure:** distinguish no matching records, unsupported mode/area, no route, and service failure. Empty results mean no matching records in the queried data, not that no amenities or homes exist. Show source and observation time where supplied; say when freshness or completeness is unknown. Do not fabricate timestamps or claim exhaustive results from a limited page. On failure, retain inputs and offer retry or an explicit change of criterion.
6. **Assessment and change:** Location supplies factual evidence. Housing supplies listing facts; recommendation assesses requirement matches and preserves `unknown` when evidence is insufficient. A changed destination or mode invalidates dependent route evidence. A changed selected home also makes the old moving quote and approval stale under the [product change rules](../product.md#changing-a-finalized-plan); unrelated housing facts may remain usable.

### Housing commute evidence

The same precision, mode, and failure rules apply to `search_housing.commute`. Its route result has no endpoint warnings or profile field; combine it with the listing's top-level `location_accuracy` and the saved destination metadata and request context. Missing destination accuracy stays unknown. Treat a match from approximate/unknown coordinates as provisional, not a confirmed housing requirement match.

Before sending a commute filter, validate the resolved destination against the deployed routing bounds for the explicitly selected city, using the same configuration as the routing service rather than administrative boundaries. Bind that validated city to `commute.city` in the filtered request and to `city` in any direct route requests; validation and execution must use the same routing area. An out-of-bounds destination stops the filtered request and produces an unsupported-area explanation without changing the requirement. If the application cannot obtain authoritative bounds, do not use a filtered search to infer coverage: use the bounded unfiltered retrieval below and direct route calls, which expose errors for actual endpoint pairs. Do not treat an arbitrary self-route probe as evidence that every listing is routable.

The existing commute filter catches `OUTSIDE_ROUTING_AREA` and `NO_ROUTE` per listing and omits their null commute results. Its `excluded_unknown_count` also includes missing-nearby cases; it is an aggregate count, not an error reason. Show it as unassessed/unknown exclusions, alongside `candidate_limit_reached`, without labeling every exclusion out-of-area or no-route. Only a bounds check or an individual route result supports a specific explanation; when neither exists, report that the reason is unavailable. Endpoint checks still apply to individual listings even when the destination is in bounds.

When candidates with unknown evidence must remain available, retrieve housing without the commute filter and route candidates individually, using their IDs where available and following the bounded procedure below. Do not silently discard them through service-side filtering. Routing metadata from the entity tool can enrich a returned result but cannot recover a home already excluded by the commute filter.

### Bounded housing fallback

Removing `commute` also removes its internal coarse-distance filter. Each fallback `search_housing` request must therefore include an explicit, disclosed spatial limit: preserve the active `bounding_box` (such as the viewport), or use `center` at the resolved commute destination with a finite `radius_m`. These forms are mutually exclusive in the current schema. Preserve the user's other supported constraints and do not silently widen a user-selected area. For a maximum-distance requirement without an existing area, derive the radius using the housing service's conservative coarse-radius policy, including its snapping allowance and margin; a plain radius equal to route length is not equivalent. If the derived radius exceeds the query limit, ask for a smaller area or disclose an explicitly agreed limited search instead of silently clipping it. For a time-only requirement, use a user-selected area or a disclosed configured radius; do not infer an exhaustive distance radius from travel time. If no valid bounded area is available, ask for one before searching.

Follow the housing response's `page.next_cursor`, sent back in the next request as `pagination.cursor`, with unchanged filters and deduplicate listing IDs. Only an explicit null next cursor indicates exhaustion; a missing or malformed cursor is a response error and leaves coverage unknown. Before starting, configure finite page, route-call, elapsed-time, and requested-result limits for the whole assessment operation; housing discovery, individual routes, and nested amenity checks share those budgets. Stop at a limit, cursor exhaustion, cancellation, or a superseding request. A result limit counts only sufficiently assessed matches. Retain the queried bounds/radius, limits, completion reason, next cursor, and fetched but unprocessed candidates. Unprocessed or failed assessments remain `unknown`, not non-matches. A continuation is an explicit new bounded pass using the preserved requirements and pending candidates. Neither a budget stop nor cursor exhaustion establishes catalogue-wide coverage.

### Searching additional amenity candidates

`find_nearby_places` has no next-nearest cursor. After its first candidate fails a walking criterion, use `search_places` with explicit `categories`, `center`, `radius_m`, and pagination; follow `next_cursor` with unchanged filters. Its order is name/ID, not distance. Deduplicate place IDs already evaluated and route each new candidate using the user's profile and the same origin. A passing route establishes a match only to the extent permitted by endpoint accuracy; a failing route rules out that candidate only.

The application must configure finite page, route-call, and elapsed-time budgets and retain the chosen search radius and completion reason with the evidence. Stop when a sufficiently supported match is found, the cursor is exhausted, a budget/deadline is reached, or the request is superseded. A user may explicitly continue a partial search using its saved cursor and remaining candidates. The radius is a disclosed retrieval boundary, not a substitute for route distance; snapping and uncertain coordinates prevent treating a naive route-length radius as exhaustive. If no match is verified, keep the housing requirement `unknown` and report what was checked, including incomplete coverage, unprocessed candidates, or failed routes. Even cursor exhaustion proves only that the queried dataset/radius was examined, not that no suitable amenity exists.

For AC-03, use a fixture where the first supermarket has a 1.3 km walking route, a second page contains one with a 900 m route and sufficiently accurate endpoints, and both are inside the configured search radius. The second result establishes a match. Repeat with a one-page budget: the expected outcome is `unknown` with a continuation available, not failure of the housing requirement. This uses the existing paginated search contract without assuming a distance-sorted or next-nearest API.

## Interaction requirements

The AI can bring up a location picker, route preview, or amenity view when it helps the current decision. Those are candidate views, not separate mandatory screens. A map click can refine a location; it does not itself choose a home or approve an order. Ordinary housing viewport changes should refresh housing results without forcing the user through another location conversation.

`/v1/housing/map` has a strict schema with no `commute` field; its `nearby` filter expresses only straight-line constraints. With routed requirements active, refresh marker/list candidates through `search_housing` using the new `bounding_box` and supported non-routed filters, leaving `commute` out so uncertain candidates remain visible. Preserve the commute and routed-amenity requirements in application state and assess returned candidates under the shared fallback budgets. Do not translate a walking requirement into `nearby` or send unsupported fields to the map endpoint. Mark candidates as pending/unknown until evaluated, and distinguish sufficiently supported matches from provisional evidence. If an additional map-endpoint layer is shown, label it explicitly as not assessed against routed requirements. Paginated or budget-limited results must indicate partial assessment; a late result for the previous viewport cannot overwrite the current view.

Provide a text/list equivalent for map candidates and route evidence, keyboard-operable selection, and readable details on narrow layouts. Show which destination and mode pending work uses; discard results superseded by a newer request. Keep pin selection, housing selection, action approval, and payment states distinct. These are requirements to verify in #28, not a claim that the prototypes or accessibility checks have been completed here.

## Non-goals and service boundaries

Housing owns listing facts; [SPEC-004: AhaMove moving service and customer-facing behavior](SPEC-004-ahamove-moving-service.md#interaction-and-boundaries) owns provider serviceability, moving quotes, and access/order-detail confirmation. The relocation application owns the single endpoint-confirmation prompt governed by this specification's precision rule (rule 2). Moving consumes that stored confirmation for the unchanged endpoint rather than repeating the address/pin confirmation; it still asks for missing or changed access and order details required by SPEC-004. A route estimate is not a moving quote or a provider promise. Map navigation/rendering and prompt placement are shared application design choices; this specification selects no map provider, SDK, or database.

Turn-by-turn navigation, continuous location tracking, worldwide coverage, arbitrary address geocoding, and automatic bookings are deferred. No new map provider, SDK, database, or service split is selected. The existing combined Location MCP can supply map and housing facts while their product responsibilities remain distinct.

## Security and operational limits

Apply the identity and authorization rules in [SPEC-008: Domain MCP tool catalogue](SPEC-008-service-tools.md#shared-contract-semantics) to saved location context and service calls. Service-token isolation is required by the [product brief's required controls](../product.md#required-controls): select credentials server-side from trusted authorization context, never from a model-supplied user ID or token; deny a call when the current user lacks the required service authorization. Do not reuse one user's grant for another user's call. Exact addresses and user-confirmed pins must remain within the authorized user's workflow; credentials must not appear in tool results shown to the model, map details, errors, or source labels. Location selection cannot authorize a paid action.

Use the service's validated spatial bounds, category limits, pagination, and routing deadlines. Do not silently widen a request or discard an unsupported requirement to fit a tool. On timeout, preserve the request and show failure/retry state; reject late results from superseded requests. Exact limits and error semantics remain authoritative in [SPEC-009](SPEC-009-tim-kiem-va-tien-ich-gan.md), [SPEC-011](SPEC-011-dinh-tuyen.md), [SPEC-013](SPEC-013-mcp-vi-tri.md), and their linked contracts.
